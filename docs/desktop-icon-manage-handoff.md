## 0. 一句话

两件事，起因是同一个：作者看到桌面图标的**锯齿**。

1. **订正图标流水线**：上一轮把 256px 原图**预降采样到 96px**，依据是"手机上每格图标约 28 像素"
   —— **把 GUI 逻辑像素当成了设备像素**。实测图标在屏幕上占 **112~268 设备像素**，

2. **新增「桌面图标管理」**（桌面「设置」App → 「桌面」分组 → 桌面图标管理）：一张与桌面槽位一一对应的 3×3 网格，

## 1. 图标流水线：错在哪、怎么修的（**这段值得完整读**）

### 症状与旧解

三张 App 图标（设置/图库/相机）放进手机后轮廓上有浅色硬边。2026-10-12 的排查得出了三条结论
并写进流水线：**颜色外扩 → 预降采样 96px → `.mcmeta(blur/clamp)`**。

### 错误前提

那段排查里有一句关键的话：**"手机上每格图标实际只有 ~28 真实像素"**。
但 28 是**GUI 逻辑像素**（`MainPage.appRect` 算出 `iconW ≈ 28~47`），
而屏幕上真正占的是 `逻辑像素 × GUI Scale`。

按代码里的排版公式重算（`iconW = (phoneWidth - 4*margin)/3`，`phoneWidth` 由
"逻辑屏高 × phoneSize × aspect"导出，再乘 GUI Scale）：

| 窗口帧缓冲 | 20:9 | 9:16 | 4:3 |
|---|---|---|---|
| 1920×1009 / 1080 | 120 px | 152 px | 200 px |
| 2560×1440 | 160 px | 200 px | 268 px |
| 854×480 | 54 px | 64 px | 88 px |

**GUI Scale 几乎不改设备像素**（逻辑屏高按 1/GUI Scale 变、再乘回去），这正是
`PhoneScreenTarget` 里"1 GUI 单位 = GUI Scale 个像素"那条设计。于是：
**正常窗口下图标一直是被放大显示的**，把 256 降到 96 = 白丢 4/5 的像素，再把 96 网格上的
硬台阶放大回去。

### 量化证据（离线重放，T = 140 设备像素）

与"面积平均理想值"比，整块图标的平均色差 MAE（0~255）：

| 源 | MAE |
|---|---|
| 原图 256 | **1.09** |
| 96px 版（旧流水线产物） | **5.07**（差 4.6 倍） |
| 256 + 去污 | 1.15（**零视觉代价**） |
| 去污 + 降到 144 / 192 | 3.92 / 2.78 |

结论：**降采样是纯损失，去污是必须的**。

### 为什么"去污"必须留

原图的**透明区 RGB 是纯白**（设置/图库/相机各 22714 / 27122 / 26376 个像素，均值 `(255,255,255)`）。
GL 的线性过滤对 RGBA 是**分通道独立插值**的（不是预乘平均），白色会被平均进轮廓 ——
作者实机看到的正是「原图的确有一点小白边」。去污（`decontaminate`）把**非全不透明**像素的 RGB
换成最近实心像素的颜色、**alpha 一个不动**，柔边完好、白边消失。

### 现在的流水线（`tools/import_manual_assets.py`）

```python
ICON_TARGET = 0        # 0 = 原图分辨率，不降采样（旧行为是 96）
ICON_BLEED  = True     # True = 只清理透明区 RGB
```

`copy_icon()` 有三种模式：默认原图直上（逐字节拷贝 + 写 `.mcmeta`）、只去污、旧降采样路径。
⚠ **别再改回 96**；那条路只在"窗口真的很小"（图标设备像素 < 96）时才可能有意义。

### 教训（可迁移）

1. **"像素"必须说清是逻辑像素还是设备像素。** 这一轮的错误就是把两者混了，而两者的比值恰好是
   GUI Scale（本机 = 4）。
2. **改素材之前先量"它在屏幕上到底多大"** —— 那个尺寸就在自己的排版代码里（`appRect`），
   不需要跑游戏就能算。
3. **"白边"有两个完全不同的来源，别混**：渲染器把 alpha 交出去了（见
   [phone-model-screen-handoff.md](phone-model-screen-handoff.md) §5.8-37），
   与贴图透明区的脏 RGB 被过滤插进来（本文 §1）。判别方法：**同一张贴图在悬浮窗与模型屏上
   是否表现不同** —— 不同 = 渲染器；一样 = 贴图。

## 2. 「桌面图标管理」

### 2.1 数据模型（三处，各司其职）

| 东西 | 位置 | 说明 |
|---|---|---|
| **稳定 key** | `MainPage.AppInfo.key`（第 77 行附近有 `KEY_TALK = "huhutalk"`） | 内置 App 用固定短名（`huhutalk`/`manual`/`settings`），附属模组用 `PhoneApp.id()` 的字符串。**刻意不用显示名**（名字会因改名/翻译失联） |
| **布局覆盖** | `HuhuTalkClientSettings.desktopSlots`（第 143 行） | `appKey → 槽位`，**稀疏**：只记玩家动过的。没有记录 = 用出厂位置（内置声明槽位 / `.slot(n)` / 自动落最小空槽） |
| **已移除** | `HuhuTalkClientSettings.desktopHidden` | 被移除的 appKey 集合。移除时会**连槽位覆盖一起清掉**（否则两个 key 会同时指向一格，谁赢取决于遍历顺序） |

两者都是 `SettingsData` 里的**可空字段** → 老配置文件天然向后兼容，**不需要版本号**。
另有 `desktopLayoutGeneration`：布局的失效版本号，与 `PhoneAppRegistry.generation()` 是
**两个独立的缓存键**（少一个就会出现"拖完要重开手机才生效"）。

### 2.2 位置的唯一决定点

`MainPage.placeByLayout()`（第 200 行）。优先级：

1. **HuhuTalk 恒定槽位 0** —— 玩家的布局数据也改不了它（配置文件被手改也挡得住）；
2. **玩家的布局覆盖**；
3. **App 自己的声明槽位**；
4. 都没有 → 最小空槽。

做法是"**稳定排序 + 依次落位**"，而不是"按下标直接赋值"：后者遇到两个 App 抢同一格时，
谁赢取决于遍历顺序（隐式、换个 Map 实现就变）。排序后落位把"谁让路"写成显式规则，
冲突方**退让到最小空槽并打 WARN** —— 沿用既有的"图标不消失"纪律。

> 玩家没动过任何图标时，全部候选同优先级、顺序 = 内置在前 + 外部按注册顺序 ⇒
> 与改造前**逐格相同**。

⚠ `AppInfo.slot` 必须等于它在数组里的下标（启动动画原点、点击命中、管理页高亮全靠这条）。
所以 `AppInfo` 保持不可变，落位时用 `withSlot(n)` **复制**一份，位置只在 `placeByLayout` 一处决定。

### 2.3 公开 API（管理页只用这些）

`MainPage` 上的静态方法：

| 方法 | 说明 |
|---|---|
| `desktopSlotCount()` / `desktopUsedCount()` | 9 / 已占几格（设置 App 那行右侧显示 `x/9 格`） |
| `desktopSlots()` | 长度恒为 9 的只读快照，下标 = 槽位 = 网格格号；**空槽 `key == null`** |
| `desktopRemoved()` | 被移除的 App（可以放回） |
| `isDesktopFixed(key)` | 是否主应用（不可移、不可删） |
| `moveDesktopApp(key, targetSlot)` | 移入；**目标格有人 = 两人换位**（不是把对方挤到别处） |
| `removeDesktopApp(key)` / `restoreDesktopApp(key)` | 移除 / 放回（主应用一律拒绝） |

`DesktopSlot` 是只读快照，把主应用那种"图标样式由设置现算"（高清/低清贴图/狐狸 emoji）
抹平成一个字段，所以管理页画出来的和桌面**长得一样**。

### 2.4 页面

`DesktopIconPage`（`phone/pages/`），与传文件页**同一套工具**：

- `PhoneGrid<Integer>` × 2（槽位网格 3 列、底部回收栏 6 列），
  `cellX/cellY` 与 `indexAt` 是渲染与命中共用的**唯一一对互逆映射**；
- 列数直接引用 `MainPage.APP_COLS`（包内可见），**不各写一个 3** —— 两处漂移管理页就对不上槽位了；
- 版式：顶部提示栏 / 中间 3×3 网格 / 底部「已移除」横栏（与传文件页同构）；
- **落位与外扩**：`cell()` 先按宽度铺满、再用"网格与回收栏之间剩下的高度"压一压，保证 3 行都在屏内；
  ⚠ 回收栏预留高度 `recycleReserve()` **刻意不与 `cell()` 互相依赖**（否则栈溢出）。

交互：

| 手势 | 行为 |
|---|---|
| 按住图标拖到另一格 | 换位（目标格有人 = 对调） |
| 按住图标拖到底部「已移除」栏 | 移除 |
| 点格子右上角 ✕ | 移除（悬停变红） |
| 点「已移除」栏里的图标 | 放回（回到出厂位置，被占则退让） |
| 主应用那格 | 右上角画一枚小白点（不是 ✕），不接受拖动起点，也不接受别人落在它那格 |

### 2.5 ⚠ 为此给输入层开的口子（**核心知识点**）

**手机里唯一的手势通路是「按住拖动 = 滚动」**：`PhoneOverlay.moveCursor` 里位移一旦超过
`DRAG_SCROLL_THRESHOLD`（4px）且主轴占优，整段手势就升级成 `mouseScrolled` 的增量，
**页面再也收不到光标位置，松开也不补点击**。`onLongPress` 要求按住 1 秒且不能移动，救不了。
⇒ **不改输入层，页面做不出真正的拖放。**

所以开了一个口子（做法与既有的 `dragAxisBoth()` / `onDragAxisResolved()` 同源）：

| 位置 | 改动 |
|---|---|
| `IPhonePage`（第 130 行起） | 新增 4 个 default 方法：`beginDragReorder` / `dragReorderTo` / `endDragReorder` / `cancelDragReorder` |
| `PhonePage`（第 401 行起） | 把它们 final 化并把坐标从"手机内容区"转成"内容坐标"，转发给 `onDragReorderStart/Move/End/Cancel` |
| `PhoneOverlay`（第 264 / 344 / 469 / 576 / 592 行） | `reorderOwner` 字段：PRESS 时问一次页面；接管后 `moveCursor` **跳过全部滚动算术**、只转发位置；RELEASE 调 `endDragReorder` 且**不补点击、不判长按**；`cancelReorderOwner()` 在掏出/收起光标时作废手势 |

**默认路径逐字节等价**：`beginDragReorder` 默认 false，`reorderOwner` 恒为 null，
上面每一处判据都不成立 ⇒ 既有页面零影响。

⚠ **踩过的坑**：接管了就**没有点击**。管理页的 ✕ 曾经因此点不动 —— 因为它压在格子里，
按下时被 `onDragReorderStart` 当成了拖动起点。修法是**在 `onDragReorderStart` 里判一次 ✕ 的
命中框、命中就返回 false 让出点击通路**。任何"格子里的按钮 + 整格可拖"的设计都要处理这一条。

## 4. 别浪费时间的地方

- **别再把图标降采样到 96**，也别按"28 像素"算任何东西 —— 那是逻辑像素（见 §1）。
- **别让 `AppInfo.slot` 与数组下标不一致**：启动动画原点、点击命中、管理页高亮都会错位。
- **别在"格子里有按钮"的地方无条件接管拖动**（✕ 点不动那次，见 §2.5）。
- **别把 `desktopSlots` 存成整张表**：附属模组随时注册/卸载，稀疏覆盖才不需要迁移；
  指向不存在 key 的记录永远不生效、也永远不碍事。
- **别在主应用上开任何口子**：`moveDesktopApp` / `removeDesktopApp` 都对 `KEY_TALK` 直接返回 false，
  而且 `wishSlot` 对它是硬编码 `SLOT_TALK`（配置文件被手改也挡得住）。
