## 本轮修正

- 修正女仆发件 **QUEUED** 归档丢失当前 turn 的适配错误：`TransferArchiveRecorder.recordQueued` 原来把 `null` 传给 `recordChunks` 的 turn 参数，只在最后一参保留 `playerMessageId`，导致本应挂到当前 turn 的 queued 事件被误生成独立 turn，并被同 turn 守卫拒绝写档。现改为把收到的 `ArchiveTurnContext` 原样传给 `recordChunks`，再进入 `ArchiveService.recordTransferEvent`。
- 当前发件链路核对为：`SendItemTool` 取得 `hc.getArchiveTurn()` → `MaidTransferService.pushBatchToPlayer(..., archiveTurn)` → `TransferArchiveRecorder.recordQueued(..., turn, ...)` → `recordChunks(..., turn, ...)` → `ArchiveService.recordTransferEvent(..., turn, ...)`。有 turn 的 queued 事件与玩家父消息同 `turnId` 并带关联消息；turn 为 null 时保持独立事件且无父消息，未删除关联、未放宽守卫。
- `recordClaimed` / `recordDropped` 仍使用独立的 null turn 上下文，本轮没有伪造父消息。
- 更新 `ArchiveService.recordEvent` 中“物品业务尚未调用”的过时基础阶段注释，说明图片与物品事件已接通、旧 system 注入等入口仍可能传 null turn；该类业务语句未改动。

代理交付时完成源码修正与编译检查，未自行运行游戏；随后用户确认图片与传输记录已储存并通过本轮验收，见上方结论。

## 归档目的与行为

### 图片、观察与回复

- 玩家通过手机新发图片时保存原图，并按内容寻址建立图片玩家消息；caption 可为空。
- 识图成功后追加同 turn 的 `OBSERVATION` 观察记录，不额外调用 LLM；识图失败追加 `SYSTEM` 失败记录。失败不会把失败图写成成功观察，原图和失败事实都保留。
- 女仆的最终文本回复归档到同一 turn，并关联玩家消息；即使发送者已离线/死亡，已得到的回复仍按当前归属校验结果保留。
- 表情作为本次回复附带的资源名文本保存，不复制图片文件、不请求模型。

### 物品事件

- **QUEUED**：女仆发件实际写入待领取箱后，按 `data.getBatch` 的实际持久化列表记录，表示“发送当时已入箱”，不代表玩家已领取。
- **CLAIMED**：领取动作完成后按逐栈真实插入数量记录；未全部插入时记 PARTIAL，不把剩余写成已领取。
- **DROPPED**：物品实体生成返回成功才记生成成功；生成失败的栈另记 FAILED，不伪造全部成功。
- P→M 物品转移记录玩家原话（可空）与主事件；部分失败另记失败补充事件且不重复玩家原话，全部失败时主事件为 FAILED。
- 既有部分失败会如实保留，不会因后续补记而变成全部成功。

### 存储、去重与兼容

- 图库按世界目录 `huhutalk_archive/assets/<sha256>.png` 保存，JSON 只保存 hash 引用；相同字节内容按同一 hash 去重，已有文件必须字节一致才复用。
- 快照当前为 schema2；读取 schema1 时只在内存中按 schema2 规范化，读取不会自动重写磁盘，只有下一次成功写入才真正落盘为 schema2。既有文字档案保持原 archiveId、消息 ID、正文和已有引用，不回填或改写历史内容。
- **新增图片/物品从本轮接通日起采集**。旧客户端历史、已有本地聊天文件不会被补档或合并，本阶段没有实现历史回填。

2. **识图失败**：制造识图失败 → 原图仍在、失败事件存在，且没有伪造成成功观察。

4. **M→P QUEUED 同 turn**：由 LLM 触发女仆发件 → 存在 QUEUED 事件且与本次玩家消息同一 turn → 部分领取、全部领取、重复领取 → 满包丢地 → 删除会话清空待领取箱，逐项核对事件与实际数量。
5. **归属守卫**：另一玩家尝试读取/领取该女仆归档或物品时被拒绝。
6. **边界时机**：关闭手机页面、切换世界后迟到的响应，客户端不应用、不解码、不创建纹理；服务端已接受的图片 turn 仍可以完成归档，不能因关页/换世界而误要求取消服务器归档。
